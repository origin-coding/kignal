# Kignal 1.0 MVP

This document defines the first MVP target for Kignal.

The goal of 1.0 MVP is to prove the core synchronous fine-grained reactivity model with the smallest useful surface area. It is not intended to be a production-grade optimized runtime or a complete ecosystem release.

## Goal

Kignal 1.0 MVP should validate that:

- A mutable source value can be represented as a signal.
- A synchronous derived value can be represented as a computed signal.
- An effect can track the signals it reads and rerun when those signals change.
- Dependencies can be cleaned up when reactive reads change between runs.
- Effects can be disposed and stop receiving future updates.
- Reactive reads can be explicitly excluded from dependency tracking with `untracked`.
- Runtime errors are propagated synchronously instead of being swallowed.

If these behaviors are correct and tested, the core feasibility of the project is established.

## Public API Scope

The MVP should include only the following public API:

```kotlin
interface Signal<out T> {
    val value: T
    operator fun invoke(): T = value
}

interface MutableSignal<T> : Signal<T> {
    override var value: T
}

interface Disposable {
    fun dispose()
}

fun <T> signal(initial: T): MutableSignal<T>

fun <T> computed(block: () -> T): Signal<T>

fun effect(block: () -> Unit): Disposable

fun <T> untracked(block: () -> T): T
```

The default usage style is explicit `.value` access:

```kotlin
val count = signal(1)

val double = computed {
    count.value * 2
}

val stop = effect {
    println(double.value)
}

count.value = 2
stop.dispose()
```

## Runtime Scope

The MVP implementation should include:

- signal value storage and notification
- dependency tracking during `computed` and `effect` execution
- computed synchronous calculation
- computed invalidation when dependencies change
- effect initial execution
- effect rerun when dependencies change
- dependency cleanup before recomputation or rerun
- effect disposal
- untracked reads
- synchronous error propagation
- single-threaded runtime assumptions

The implementation should prioritize clear behavior and readable internals over performance optimizations.

## Acceptance Tests

The MVP is complete when these behaviors are covered by tests:

- `signal` can read and write `.value`.
- `computed` calculates synchronously from a signal.
- `computed` returns updated values after dependencies change.
- `effect` runs once immediately.
- `effect` reruns when a tracked signal changes.
- `effect` does not rerun after disposal.
- Dynamic dependency switching removes old dependencies.
- `untracked` reads do not become dependencies.
- `computed` errors propagate to the reader.
- `effect` errors propagate during initial execution and synchronous reruns.

Dynamic dependency switching should be verified with a test like:

```kotlin
val enabled = signal(true)
val a = signal(1)
val b = signal(10)

val result = computed {
    if (enabled.value) a.value else b.value
}

assertThat(result.value).isEqualTo(1)

enabled.value = false
assertThat(result.value).isEqualTo(10)

a.value = 2
assertThat(result.value).isEqualTo(10)

b.value = 20
assertThat(result.value).isEqualTo(20)
```

## Explicit Non-Goals

The following features are intentionally outside the 1.0 MVP:

- `batch`
- `scope`
- scheduler abstraction
- asynchronous effects
- coroutine support
- Flow interop
- Reactive Streams interop
- Reactor interop
- resource support
- delegated property syntax
- Kotlin Multiplatform
- thread-safety guarantees
- JMH benchmarks
- low-level graph optimizations

These can be planned after the core reactive graph semantics are proven.

## Suggested Implementation Order

1. Add the public interfaces and factory functions.
2. Implement basic `signal` read/write behavior.
3. Implement dependency tracking context.
4. Implement `effect` with initial run, rerun, cleanup, and disposal.
5. Implement `computed` with synchronous cached reads and invalidation.
6. Add dynamic dependency cleanup tests.
7. Add `untracked` for reads that should not be collected as dependencies.
8. Add synchronous error propagation tests.
9. Refine internals only after the MVP behavior is covered.
